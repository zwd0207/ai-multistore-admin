# 紫鸟接入研究最终摘要

## 1. 紫鸟能为系统增加什么

紫鸟最有价值的不是替代 Naver/Coupang API，而是补齐“店铺环境与权限控制层”：

- 自动发现公司名下的紫鸟店铺。
- 把紫鸟店铺和内部 Store 建立人工确认绑定。
- 识别店铺平台、站点、标签和平台登录账号状态。
- 检查店铺绑定的设备、套餐、地区、到期和续费状态。
- 核对员工能进入哪些店铺。
- 对比内部 RBAC 和紫鸟授权是否一致。
- 把设备到期、权限漂移和绑定缺失放进今日工作台。
- 未来经独立审批后，从系统内打开正确的紫鸟店铺。
- 在官方 API 缺失时，为人工提供受控浏览器入口。

## 2. 最值得优先接入的能力

按价值和风险排序：

1. 公司 ID 只读识别。
2. 公司全部店铺只读查询。
3. 指定员工可访问店铺只读查询。
4. 店铺授权用户只读查询。
5. 店铺平台、站点和标签读取。
6. 设备状态和到期读取。
7. 设备历史绑定读取。
8. 内部 Store ↔ 紫鸟店铺人工确认绑定。
9. 工作台环境健康提醒。
10. 后置的一键打开正确店铺。

前 8 项可以形成稳定只读闭环；SSO 和浏览器自动化应后置。

## 3. 可以替代的人工工作

- 手工登记紫鸟店铺 ID、平台和设备信息。
- 逐店核对员工是否有权限。
- 逐店查看设备或套餐是否即将到期。
- 在内部系统和紫鸟之间反复确认店铺对应关系。
- 出现 API 缺失时手工寻找正确店铺入口。

## 4. 不能替代 Naver/Coupang 官方 API

当前紫鸟公开 ERP API 没有证明能提供 Naver/Coupang 的以下结构化业务数据：

- 商品、选项、价格和库存。
- 订单、收件信息、取消和售后。
- 客服咨询和回复。
- 发货和物流状态。
- 广告、销售、结算和财务明细。

这些继续使用现有 Naver/Coupang 官方 API。浏览器能打开或抓取页面，不代表紫鸟提供了稳定业务 API。

## 5. API 和 Skill 盘点结果

- 紫鸟浏览器 ERP API：5 个核心分组。
- 当前目录：74 条记录、73 个唯一 API ID。
- 加上公司信息、应用 Token、用户登录 Token：共登记 76 个唯一服务端端点。
- 回调：1 个消息推送组，包含会员到期、监管告警、访问申请和截图证据。
- SSO Schema：3 个客户端 Action。
- Webdriver：11 个本地 Action。
- SkillHub：121 个 Skill、6 个分类。
- 与本项目紫鸟接入直接相关：ERP、SSO、Webdriver/CDP 3 个；图片工具是可选的第 4 个。
- Naver/Coupang 专用 Skill：0 个。

## 6. ERP-Demo 可以复用什么

可复用的是协议知识：

- 七个公开路径和主要字段。
- App Token、员工、店铺、授权和 SSO 的调用顺序。
- 店铺列表和一键启动的交互思路。
- 请求/响应模型的基本形态。

不能复用的是安全实现：

- 固定 119/29 分钟 Token 缓存。
- 记录完整请求/响应。
- 把 SSO Token 放入前端 URL。
- YAML 明文配置凭证。
- 无审批、无幂等、无回滚的授权写入。

Demo 使用 Java/RuoYi/Vue，当前系统使用 Python/FastAPI/React，不适合复制代码。

## 7. 当前系统与紫鸟的重叠

当前系统已经有：

- Store、设备环境、平台登录账号和 API 凭证。
- 用户、角色、权限、MFA、店铺成员关系。
- 商品、订单、咨询、邮箱、销售、结算和物流。
- SyncLog、SyncCheckpoint、ApiCapability、操作审计。
- 店铺开通、自动读取、异常中心和今日工作台。

因此后续主要扩展“公司级连接和外部映射”，不重新建设店铺、订单、用户、同步和工作台。

确认缺失：

- 公司级外部连接。
- 内部 Store ↔ 紫鸟 store ID 映射。
- 内部用户 ↔ 紫鸟 user ID 映射。

## 8. 仍需人工登录确认

- 企业是否唯一绑定、认证是否完成。
- 应用是否唯一、鉴权模式和审核状态。
- 首批只读权限是否已批准，写权限是否为空。
- IP 白名单规则。
- QPS、日配额、分页上限和错误码。
- SDK 推荐版本和弃用政策。
- SSO Token 权限、有效期、撤销和重放规则。
- Webdriver 是否开通、允许账号和客户端版本。
- CLI 应用、终端绑定和只读权限能力。
- 回调签名、去重、截图权限和安全管家有效期。
- 74 个返回 403 的 Skill 包是否需要登录或链接已失效。

## 9. 第一项最小安全扩展任务

推荐做 **“紫鸟店铺发现与人工匹配 Mock”**：

- 只使用虚构公司、员工、店铺和设备数据。
- 复用现有 Store、DeviceEnvironment、ErpUser、ErpStoreMembership、ApiCapability、SyncLog 和 Dashboard。
- 只生成匹配候选，人工确认后才形成绑定。
- 不保存真实凭证。
- 不连接紫鸟。
- 不启动店铺。
- 不实现任何授权、设备或平台写入。

这项任务最能提前验证最终产品流程，同时不承担真实账号风险。
