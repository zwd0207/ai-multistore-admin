# T03.5 仓库发货隐私与操作规则

## 0. 决策结论

此前“普通订单列表不显示完整收件信息”的决定作废，本文为运营版 V1 的唯一适用规则。

授权运营人员在其被分配店铺的订单处理和仓库发货页面，可以直接看到完成工作所需的完整收件人姓名、联系电话、邮编、地址和配送备注。这里的“完整显示”不是公开显示，也不是所有登录用户可见；它必须同时满足业务页面白名单、人员权限和店铺范围三项条件。

核心原则：

1. 工作页面可用：不能为了形式脱敏，让运营人员再次登录平台或打开 Excel 查地址。
2. 用途限定：完整信息只用于订单核对、仓库发货、配送异常和经授权的售后处理。
3. 查看与导出分权：能看不代表能下载；导出权限单独授予。
4. 服务端授权：前端隐藏不是权限控制，所有查询、导出、下载和写回都由后端校验角色、店铺和批次。
5. 日志最小化：业务记录可以保存履约需要的数据，日志、审计、统计、报错和遥测不得复制完整收件信息。
6. 人工确认聚焦真实风险：日常查看不反复弹窗；文件离开系统和真实平台写回必须明确确认。

## 1. 可以显示完整收件信息的运营页面

### 1.1 直接完整显示

以下页面在权限和店铺范围通过后，可以直接显示完整收件信息，不需要逐行点击“解密”或每次弹窗确认：

| 页面 | 允许显示的完整字段 | 使用目的 |
| --- | --- | --- |
| 订单处理列表 | 收件人姓名、联系电话、邮编、完整地址、配送备注 | 批量核对待发货订单、发现地址和联系方式异常 |
| 订单详情 | 同上 | 单笔订单核对、修改前确认、异常处理 |
| 仓库发货 - 待生成批次 | 同上 | 创建批次前核对收件信息与货品 |
| 仓库发货 - 批次详情 | 同上 | 确认即将交给仓库的订单范围 |
| 仓库发货 - 导出预览 | 同上 | 下载前核对仓库表内容 |
| 仓库发货 - 仓库回传校验 | 同上，但页面重点仍是运单与异常 | 对照仓库回传、处理错单和漏单 |
| 配送/售后异常详情 | 与当前异常直接相关的订单收件字段 | 地址错误、拒收、退回、改址等处理 |

订单处理列表属于授权工作页面，因此不得以“普通列表”为由只显示掩码。列表可通过列显示设置减少视觉拥挤，但这只是界面偏好，不能让运营人员失去查看完整字段的能力。

### 1.2 按任务显示

客户咨询页面默认展示订单号、商品、发货阶段、物流公司和运单进度。遇到地址确认、联系电话确认、配送失败或售后取件等需要收件信息的咨询时，具有 `recipient_pii.view` 权限的客服可在关联订单侧栏查看完整信息，并产生一次“查看关联订单收件信息”的审计事件。

普通配送进度咨询不需要主动铺开完整地址，以免客服页面长期展示与当前问题无关的信息；但这不是禁止客服查看，而是按任务展开。

### 1.3 禁止显示完整信息

以下页面和载体不得出现完整收件信息：

- 今日工作台的统计卡片、待办数量和完成摘要。
- 销售统计、经营分析、库存、商品、店铺管理和平台连接页面。
- 批次历史列表、导出历史列表和平台回填历史列表；这些列表只显示批次号、店铺、数量、操作者和结果。
- 操作日志、审计日志、同步日志、错误日志和开发控制台。
- Toast、系统通知、邮件主题、任务标题、URL、查询参数和浏览器标题。
- AI 提示词、AI 日报、分析数据集和第三方遥测。
- 未经授权的截图、打印预览和公开分享链接。

## 2. 人员、店铺范围与权限

### 2.1 固定权限键

Terra 必须实现以下独立权限，不能继续用一个笼统的 `orders.read` 覆盖全部能力：

| 权限键 | 能力 |
| --- | --- |
| `recipient_pii.view` | 在白名单工作页面查看完整收件信息 |
| `recipient_pii.export` | 生成和下载包含完整收件信息的仓库发货表 |
| `recipient_pii.cs_reveal` | 在客户咨询中按关联订单展开完整收件信息 |
| `shipping.batch.manage` | 创建批次、提交仓库、上传回传表和处理校验结果 |
| `shipping.writeback.approve` | 确认并执行 Naver 发货回填 |
| `recipient_pii.audit.read` | 查看谁在何时查看/导出过数据的审计元数据，不包含原始收件信息 |

所有权限都必须叠加 `assigned_store_ids`。用户即使有权限键，也不能查看、导出或回填未分配店铺的数据。批次必须固定一个 `store_id` 和一个 `platform`，不允许跨店批次。

### 2.2 角色基线

| 人员 | 完整查看 | 导出仓库表 | Naver 回填 | 说明 |
| --- | --- | --- | --- | --- |
| Owner | 所有店铺 | 可以 | 可以 | 全局业务负责人 |
| Admin | 已分配店铺 | 可以 | 可以 | 必须显式拥有对应权限键 |
| 订单运营 | 已分配店铺 | 默认不可以 | 默认不可以 | 负责订单核对；需要兼任发货时再授予导出权限 |
| 仓库发货运营 | 已分配店铺 | 可以 | 只有额外授权才可以 | V1 的主要导出角色 |
| 客服 | 仅关联订单，按任务展开 | 不可以 | 不可以 | 需要 `recipient_pii.cs_reveal` |
| 售后运营 | 已分配店铺的异常详情 | 默认不可以 | 不可以 | 仅处理当前售后任务 |
| 审计员 | 不可以查看原始值 | 不可以 | 不可以 | 只看访问和操作元数据 |
| Viewer/只读观察者 | 不可以 | 不可以 | 不可以 | 只看无收件隐私的汇总 |

外部仓库人员默认不登录运营系统。仓库通过当前批次的受控文件取得履约信息，不获得其他订单、历史批次或店铺数据。未来若建立仓库账号，应使用独立的 `warehouse_worker` 角色，只能访问被指派批次，不能浏览订单中心或导出历史。

### 2.3 权限实施要求

- 权限由后端会话身份和数据库成员关系计算，禁止信任前端传入的 `actor_context.role`、`manual_approval=true` 或店铺 ID。
- 订单查询接口必须按页面用途拆分响应合同。运营工作接口可返回完整字段；工作台、统计、日志和历史接口不得复用同一全量 DTO。
- 未授权响应必须不包含字段，而不是返回完整值后由前端遮盖。
- 批量查询、单笔查询、导出和下载均执行同样的店铺范围检查。

## 3. 仓库发货表字段

### 3.1 必须包含的收件字段

每个发货行必须包含：

1. `receiver_name`：收件人姓名。
2. `receiver_phone`：收件人完整联系电话。
3. `zip_code`：邮编。
4. `receiver_address_line1`：基础地址/道路名地址。
5. `receiver_address_line2`：详细地址，包括楼层、门牌和房号；源平台只有一个地址字段时，导出为 `receiver_address_full`，不得用不可靠的字符串规则强拆。
6. `receiver_address_full`：供仓库直接使用的完整合并地址。
7. `delivery_memo`：门禁、放置位置、联系要求等配送备注。

仅当平台订单明确提供备用联系电话，且仓库实际需要时，才增加 `receiver_phone_secondary`。买家电话不得自动冒充收件人电话；若业务规则允许在收件电话缺失时使用买家电话，必须在导出前标记“联系方式待确认”，由运营确认后才进入批次。

### 3.2 仓库表的完整最小合同

除收件字段外，仓库表必须包含以下履约字段：

- 只读系统列：发货批次号、平台、店铺名称、平台订单号、平台商品订单号、内部 SKU/货号、商品名称、规格/选项、订单数量。
- 收件列：上一节全部字段。
- 仓库填写列：实际发出货号、实际发出数量、物流公司、运单号、发货时间、异常原因、仓库备注。

平台订单号、平台商品订单号、批次号和系统预填收件字段必须保护为只读单元格。仓库填写列应使用固定列名和数据校验，避免修改系统列后无法匹配。

不应进入仓库表的字段：订单金额、支付方式、客户咨询内容、账号凭证、内部利润、风险备注、用户 ID、审计 ID、平台原始响应。

### 3.3 文件命名与保存

- 文件名只使用批次号、店铺短标识和日期，例如 `SHIP-20260710-001_store-12.xlsx`，不得包含收件人姓名、电话或订单商品名。
- 下载响应不得暴露服务端绝对 `file_path`。
- 文件通过短时下载令牌取得；令牌绑定用户、店铺、批次和单次/有限次数使用。
- 文件内容应存放在受控存储中并采用静态加密；下载使用 HTTPS。
- V1 建议完成批次后 30 天自动删除文件正文，只保留无收件信息的导出元数据和 SHA-256。若公司或平台规则要求不同期限，由管理员配置，但不得无限期默认保存。
- 仓库回传文件验证并提取物流字段后，不再长期保存完整文件；保留期限与导出文件一致或更短。

## 4. 避免收件信息进入无关日志和记录

### 4.1 审计记录允许保存

审计日志只保存：

- 操作者内部 ID/不可逆标识、角色和店铺范围。
- 动作：查看详情、客服展开、生成导出、下载、上传、确认回填。
- 店铺 ID、平台、批次 ID、订单数量、成功/失败数量。
- 订单目标使用内部 ID 或不可逆哈希；不得保存完整订单快照。
- 文件名、文件 SHA-256、文件大小、下载令牌 ID 哈希和到期时间。
- 时间、结果、错误码、请求关联 ID。

审计日志不得保存姓名、电话、邮编、地址、配送备注、Excel 行内容、HTTP 请求体、平台原始响应或文件正文。

### 4.2 应用与基础设施日志规则

- 对订单和发货路由关闭请求体、响应体和查询参数记录；只记录路由模板、状态码、耗时和关联 ID。
- 错误信息只返回行号、字段名和业务错误码，例如 `row=12, field=tracking_number, code=required`，不得拼接整行数据。
- 前端 `console.log`、错误上报、性能监控和产品分析事件不得携带订单对象、表格行或完整 API 响应。
- 禁止把收件信息放入 URL、路由状态、localStorage、sessionStorage、Redux 持久化、缓存键或通知文本。
- 搜索日志只记录“执行了订单搜索”和结果数量，不记录姓名、电话、地址等搜索词。
- 平台 `raw_data` 属于受限业务原始记录，不能复制到同步日志或审计日志；访问权限至少与 `recipient_pii.view` 相同，并设置单独保留策略。
- 数据库备份、错误转储和测试夹具不得把生产收件信息复制到开发环境；测试统一使用明显虚构数据。

### 4.3 脱敏展示规则

不在白名单页面时，若确需识别订单，可显示：收件人姓氏/首字符、电话末四位、地址到市/区级。脱敏值应由后端生成专用字段，不能把完整值发送给前端再用 CSS 隐藏。

## 5. 下载、导出和平台回填的人工确认

### 5.1 查看

授权运营人员进入订单处理和仓库发货白名单页面时，不需要重复确认。系统记录正常访问事件即可。这样既保护数据，也不破坏每日高频工作效率。

### 5.2 生成并首次下载仓库表

点击“生成并下载仓库表”后，显示一次业务确认，必须明确列出：

- 平台和店铺。
- 发货批次号。
- 订单数和商品件数。
- 将包含姓名、联系电话、邮编、完整地址和配送备注。
- 接收方仓库名称。
- 货号未匹配、库存不足、地址/电话缺失、取消订单等阻断数量。

确认文案使用“我确认此批次将发送给指定仓库用于发货”。有任何阻断项时按钮不可用；待确认项必须逐项处理或有权限地标记例外。确认后服务端再次校验权限、店铺、批次版本和订单状态，再生成短时下载令牌。

首次生成和下载可合并为一次确认，避免连续两个无意义弹窗。文件过期后的重新生成、不同用户下载或再次下载都需要新的确认和审计记录。单纯打开导出预览不产生文件，也不需要确认。

### 5.3 上传仓库回传表

选择文件后先显示批次、店铺、文件名、行数和解析结果。解析预览不写平台，不要求危险操作确认。点击“确认导入回传结果”时确认批次和店铺，随后只写本地回传记录；缺失、重复、错店和无法匹配的行进入阻断或待确认组。

### 5.4 Naver 发货回填

真实回填必须由拥有 `shipping.writeback.approve` 的人员主动发起，最终确认页面必须显示：

- Naver 店铺名称和店铺 ID。
- 发货批次号、待回填订单数、商品订单数。
- 每行平台商品订单号、物流公司、运单号和当前平台状态。
- 可写入、待确认、阻断三组及失败原因。
- “本操作会把物流信息写入真实 Naver 店铺”的明确提示。

确认前服务端必须重新读取或校验平台当前状态，拦截已取消、已发货、终态、店铺不匹配、批次版本变化和重复幂等键。用户勾选“我已核对店铺、订单和物流信息”后才能执行。前端不得预先提交所有确认布尔值为 `true`；后端必须用短时、一次性的 approval token 绑定当前用户、批次版本、候选行哈希和店铺。

回填后逐行显示成功或失败，失败行保留在待办中。重试只针对失败行，再次执行前重新预检和确认，不允许整批无差别重放。

回填确认页面不需要展示完整收件地址；此操作核对的是商品订单号与物流信息，减少无关暴露。

## 6. Terra 执行标准

### 6.1 后端必须完成

1. 在正式权限模型中增加本文六个权限键，并按用户成员关系与 `assigned_store_ids` 服务端判定。
2. 将订单响应拆成至少三类合同：
   - `OrderOperationsRead`：授权订单/发货页面，可含完整收件字段。
   - `OrderSummaryRead`：工作台、统计和历史列表，不含完整收件字段。
   - `OrderCustomerServiceRead`：默认脱敏，具有客服展开权限时由单独接口返回关联订单完整字段。
3. 禁止通用 `GET /orders` 无条件向所有角色返回 `raw_data` 和完整收件字段；返回内容必须由用途明确的端点与权限决定。
4. 扩展发货导出合同，使用本文收件字段。移除“只要包含收件字段就阻断”的旧逻辑，改为校验 `recipient_pii.export`、店铺范围、批次状态和导出确认凭证。
5. 提供受控文件下载接口，返回文件流或对象存储签名响应，不返回服务端路径；下载令牌绑定用户、批次、店铺、有效期和使用次数。
6. 导出、下载、客服展开和回填写入无 PII 审计事件。建立审计 payload allowlist，发现收件字段时拒绝写入日志而不是先写后清理。
7. 平台回填使用服务端生成的 approval token，绑定 `user_id + store_id + batch_id + batch_version + candidate_hash + expires_at`，执行后立即失效。
8. 为导出文件和上传文件提供到期清理任务；清理结果只记录文件哈希和批次 ID。

### 6.2 前端必须完成

1. 订单处理列表、订单详情和仓库发货白名单页面，对有权人员直接显示完整收件字段；不得默认用星号替代，也不得要求逐行点开。
2. 无权人员不渲染相关列或入口；禁止先拿完整值再前端遮盖。
3. 客服页仅在关联订单任务中提供“查看收件信息”，按权限调用专用接口；关闭侧栏后从组件状态移除完整对象。
4. 导出确认、重新下载确认、回传导入确认和 Naver 最终确认严格使用本文文案与字段，不显示技术门禁词。
5. 页面错误、Toast、日志和遥测只使用批次号、行号、数量和业务错误文案。
6. 页面刷新后不把收件信息写入浏览器持久化；重新从受权 API 获取。

### 6.3 固定 API/字段合同

完整收件对象统一为：

```json
{
  "receiver_name": "string",
  "receiver_phone": "string",
  "receiver_phone_secondary": "string|null",
  "zip_code": "string",
  "receiver_address_line1": "string|null",
  "receiver_address_line2": "string|null",
  "receiver_address_full": "string",
  "delivery_memo": "string|null"
}
```

禁止前后端继续并存 `receiverName`、`receiver_name`、`address`、`receiverAddress` 等多套业务字段。平台适配层负责映射为上述 snake_case 合同。

权限拒绝统一返回 `403` 和稳定业务码：

- `recipient_pii_view_forbidden`
- `recipient_pii_export_forbidden`
- `recipient_pii_store_scope_forbidden`
- `shipping_writeback_approval_forbidden`
- `shipping_approval_token_invalid`
- `shipping_approval_token_expired`
- `shipping_batch_version_changed`

错误响应不得回显请求中的姓名、电话、地址、配送备注或整行 Excel 数据。

### 6.4 必须通过的验收测试

1. 有 `recipient_pii.view` 且被分配该店铺的订单运营，可在订单列表和发货页面取得完整收件字段。
2. 同一人员访问未分配店铺返回 `403`，响应体不含任何收件字段。
3. 只有查看权限、没有导出权限的人员不能生成或下载仓库表。
4. 仓库发货运营导出的 XLSX 包含本文全部必需收件字段和仓库回填列。
5. 导出确认记录只含批次、店铺、操作者、数量和文件哈希，不含 PII。
6. 客服只有在咨询关联订单且具有 `recipient_pii.cs_reveal` 时可展开完整信息，且产生无 PII 审计事件。
7. Dashboard、统计、历史、日志和审计 API 响应中扫描不到姓名、电话、地址、邮编和配送备注。
8. 后端异常、前端遥测和测试输出扫描不到真实或夹具中的完整收件信息。
9. 下载令牌不能跨用户、跨店铺、跨批次使用，过期和重复超限均失败。
10. 回填 approval token 不能用于不同批次或变化后的批次版本，使用一次后失效。
11. Naver 回填最终确认页面显示店铺、订单和物流影响范围，但不复制完整地址。
12. 所有测试使用虚构收件信息、临时数据库和禁用真实平台写入的环境。

### 6.5 完成定义

Terra 只有在上述权限合同、页面白名单、仓库表字段、日志 allowlist、受控下载、人工确认和 12 项验收测试全部落地后，才能将 T03.5 标记为实现完成。仅在页面增加掩码、复选框或提示文案不算完成。

## 7. 对现有实现的明确修正

- `OrderRead` 当前包含完整收件字段与 `raw_data`。完整字段本身不是错误，但不能继续作为所有页面和所有角色共用的无条件响应。
- 现有 `evaluate_real_excel_generation_mock_gate` 遇到 `include_receiver_privacy=True` 即阻断。这与真实仓库流程冲突，实施时应替换为受权导出门禁。
- `ShippingExportBatch.include_receiver_privacy` 应表示该文件确实包含收件信息并触发相应权限、审计和保留策略，不应作为永久禁止标志。
- `privacy_fields_redacted=True` 只能描述日志和审计元数据已排除 PII，不能用于宣称仓库履约文件本身已脱敏。仓库文件必须含完整收件字段，二者语义需要分开。
- 当前基于客户端 `actor_context` 和确认布尔值的门禁只能用于 mock 验证，不能作为生产授权依据。

本文解决的不是“是否允许运营看到客户信息”，而是“让真正需要处理订单的人看得到，让无关页面、无关人员和无关记录永远拿不到”。
