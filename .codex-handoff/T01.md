## V1 产品目标与边界

运营版 V1 的唯一目标是让普通运营人员完成一个 Naver 店铺从待发货订单到仓库发货、物流回传、平台回填和客服查询的完整流程：

```text
平台待发货订单
→ 匹配内部货号和仓库库存
→ 创建发货批次
→ 下载并发送仓库表
→ 仓库回填物流公司和运单号
→ 上传系统校验
→ 人工确认
→ 回填 Naver
→ 客服查询订单发货进度
```

固定边界：

- Naver-first；V1 不扩展 Coupang/Gmarket 发货写回。
- 一个发货批次只能属于一个店铺和一个平台。
- 仓库提前备货，不设计接单采购流程。
- 真实平台回填必须由运营人员逐批次确认。
- 不做 AI 自动发货、自动回复或自动改库存。
- 完成度按运营闭环验收，不按 Phase、页面或接口数量计算。

## 2. 首页今日待办结构

首页第一屏只显示可操作任务，不展示能力说明、接口状态或长篇 SOP。

| 待办 | 优先级 | 点击目标 |
|---|---:|---|
| 回填失败 | 紧急 | 失败记录与原因 |
| 取消订单发货拦截 | 紧急 | 被发货流程命中的取消订单 |
| SKU 未匹配 | 高 | 待维护内部货号的订单 |
| 库存不足 | 高 | 库存阻塞订单 |
| 待生成发货批次 | 高 | 可加入批次的订单 |
| 等待仓库返回 | 中 | 已发仓库的批次 |
| 仓库回传待核对 | 高 | 正常、待确认、阻塞三组结果 |
| 待平台回填 | 高 | 最终人工确认页面 |
| 客服未回复 | 高 | 待回复咨询 |
| 今日已完成 | 信息 | 今日完成订单和处理结果 |

数字必须区分 `0` 与“无法确认”。无法确认时显示“待更新”，不得显示为 0。每个待办必须直接打开已带筛选条件的目标列表。

## 3. 仓库发货五阶段状态机

| 阶段 | 后端状态 | 普通页面名称 |
|---|---|---|
| 1 | `BATCH_PREPARATION` | 待生成发货批次 |
| 2 | `WAREHOUSE_WAITING` | 已发仓库，等待回传 |
| 3 | `RETURN_REVIEW` | 仓库回传待核对 |
| 4 | `PLATFORM_WRITEBACK` | 待平台回填 |
| 5 | `FINISHED` | 已完成与失败 |

第五阶段包含 `COMPLETED`、`COMPLETED_WITH_ERRORS` 和 `CANCELLED`。成功记录不可修改；失败记录修正后只能单独重试。

## 4. 每阶段操作与完成条件

| 阶段 | 允许操作 | 完成条件 |
|---|---|---|
| 待生成批次 | 更新订单、筛选、修正 SKU、确认库存、勾选订单、预览并创建批次 | 所有入选订单同店铺同平台，通过取消检查、SKU 匹配和库存检查，批次及 Excel 生成成功 |
| 等待仓库回传 | 下载或重新下载仓库表、标记已发仓库、上传回传表、在仓库未实际发货前取消批次 | 仓库回传表上传且解析成功 |
| 回传待核对 | 查看正常/待确认/阻塞、修正物流公司和运单号、排除取消订单、确认回传 | 所有行完成分类，无“未核对”记录，至少一条可回填 |
| 待平台回填 | 查看逐单明细、执行预检查、人工勾选确认、提交 Naver、单条重试 | 所有可回填行获得成功或明确失败结果 |
| 已完成与失败 | 查看结果、导出失败清单、修正失败记录后重试 | 成功行永久完成；失败行保留原因和处理入口 |

强制规则：

- 一个订单不得同时进入两个活动批次。
- 取消、退货、换货和已发货订单必须在创建批次与平台回填前各检查一次。
- 订单号、商品订单号和批次号不得由仓库修改。
- 物流公司、运单号或数量异常必须停在人工核对阶段。
- 批次成功回填记录不可删除或重新发送。

## 5. 订单、发货、客服数据关系

```text
Store
├─ Order
│  ├─ LogisticsInventoryMapping / LogisticsInventoryItem
│  ├─ ShippingBatchRow
│  ├─ TrackingImportRow
│  ├─ PlatformWritebackResult
│  └─ CustomerInquiry
└─ ShippingBatch
   ├─ ShippingBatchRow[]
   ├─ currentTrackingImportBatch
   └─ PlatformWritebackResult[]
```

关系规则：

- 订单是业务主对象，所有发货记录必须通过本地 `order_id` 关联订单。
- 同时保留平台订单号和商品订单号用于仓库及平台核对。
- 发货批次是一组同店铺、同平台订单的工作容器。
- 仓库回传批次必须关联发货批次；回传行必须关联发货批次明细及订单。
- 客户咨询新增可为空的 `order_id`；匹配后直接关联订单。
- 订单详情返回当前发货阶段、批次号、仓库回传、物流和平台回填摘要。
- 客服详情返回订单、商品、发货批次、仓库进度、物流和平台回填摘要。
- 收件信息从订单读取，仅进入受控仓库文件，不复制到批次摘要、审计日志或同步日志。

## 6. 普通运营验收标准

1. 新运营人员培训不超过 15 分钟即可完成一次模拟发货。
2. 首页进入任一待办只需一次点击，高频任务最多三次主要操作。
3. 页面刷新、退出重进后，批次、回传和回填状态不丢失。
4. 不需要逐条复制物流单号。
5. 不允许跨店铺创建批次或执行平台回填。
6. 不允许重复批次、重复回填、取消订单误发。
7. 每条失败记录必须显示普通中文原因和下一步操作。
8. 客服人员两次点击内可看到订单、仓库和物流进度。
9. 真实回填前逐单展示店铺、订单、物流公司、运单号和影响范围。
10. 同一请求重复点击不得重复创建批次或重复回填。
11. 页面正常状态下不展示技术诊断和系统实现说明。
12. 一个真实 Naver 店铺连续 5 个工作日无错店、漏单、重复发货后，V1 才通过。

## 8. 普通页面禁止术语

禁止显示：

`API`、`endpoint`、`token`、`secret`、`credential`、`HMAC`、`JSON`、`raw response`、`store_id`、`mock`、`backend`、`frontend`、`gate`、`readonly`、`hash`、`correlation_id`、HTTP 状态码、数据库表名、能力矩阵。

固定替换：

| 禁止表达 | 普通运营表达 |
|---|---|
| 手动同步 | 更新平台数据 |
| writeback | 平台回填 |
| tracking import | 导入仓库回传表 |
| blocked | 暂时不能处理 |
| credential not ready | 店铺连接资料需要管理员处理 |
| id-hash | 不展示；使用业务订单号或“内部记录” |

### 运营接口

| 方法与路径 | 作用 |
|---|---|
| `GET /shipping/workbench` | 返回五阶段、异常和今日完成计数 |
| `POST /shipping/batches` | 校验订单并创建单店铺批次 |
| `GET /shipping/batches` | 按阶段查询批次 |
| `GET /shipping/batches/{id}` | 返回批次完整业务详情 |
| `POST /shipping/batches/{id}/mark-sent` | 标记已发送仓库 |
| `GET /shipping/batches/{id}/download` | 下载受控仓库 Excel |
| `POST /shipping/batches/{id}/warehouse-return/preview` | 上传并校验仓库回传表 |
| `POST /shipping/batches/{id}/warehouse-return/confirm` | 人工确认后保存回传记录 |
| `POST /shipping/batches/{id}/writeback-preview` | 平台回填前重新检查 |
| `POST /shipping/batches/{id}/writeback` | 人工确认后执行 Naver 回填 |
| `POST /shipping/batches/{id}/retry-failed` | 只重试修正后的失败行 |
| `GET /orders/{id}/fulfillment` | 返回订单发货全过程 |
| `GET /customer-inquiries/{id}/order-context` | 返回客服所需订单和物流上下文 |

### 仓库 Excel 合同

系统填写：批次号、平台、店铺、订单号、商品订单号、内部货号、商品、规格、数量、收件人、电话、邮编、地址、配送备注。

仓库填写：实际货号、实际数量、物流公司、物流公司代码、运单号、发货时间、异常原因、仓库备注。

原始上传文件解析后不长期保存。包含收件隐私的导出文件默认保留 7 天；批次元数据、回填结果和审计证据按运营保留策略保存。下载必须校验店铺访问范围。
