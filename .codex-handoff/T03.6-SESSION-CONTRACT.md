# T03.6 Production Session Contract

## 0. 唯一决策

运营版 V1 使用：

> 服务端不透明会话 + `HttpOnly` 安全 Cookie + CSRF 防护 + 数据库实时授权。

不使用浏览器保存 JWT，不使用页面传入用户 ID，不使用 `X-ERP-User-Key` 作为生产身份，不接受 `actor_context.role`、`store_ids`、`is_admin` 或任何前端布尔值作为授权证据。

登录成功后，服务端生成高熵随机会话凭证。浏览器只通过 Cookie 自动携带该凭证；服务端只保存凭证哈希，并在每个受保护请求中重新确认会话、用户状态和授权版本。

生产会话与开发测试身份是两套互斥能力。生产进程发现开发身份开关、测试密钥、不安全 Cookie 或通配 CORS 时必须拒绝启动，而不是打印警告后继续运行。

## 1. 登录、退出、过期和强制失效

### 1.1 登录前提

只有同时满足以下条件的用户可以登录：

1. `erp_users.status = active`。
2. 已配置可用认证方式，不能是 `local_pending`。
3. 至少存在一个有效店铺成员关系，或属于明确的系统 Owner 管理范围。
4. 生产 MFA 已完成配置。
5. 用户、认证方式和组织均未被管理员禁用。

V1 允许两种生产认证来源：

- 本地密码：登录标识规范化后查询，密码使用 Argon2id 哈希验证。
- 企业 SSO：由受信任身份提供方完成认证；必须验证签名、issuer、audience、nonce、state 和回调地址。

两种来源最终都只能创建同一种服务端会话。SSO 返回的邮箱、角色或店铺声明不能直接成为 ERP 权限；只用于找到已存在且已激活的 ERP 用户。

### 1.2 MFA

- 所有生产运营账号必须启用 MFA。
- 首选 WebAuthn/Passkey；可接受 TOTP 作为 V1 方案。
- Owner、Admin、具有 `recipient_pii.export` 或 `shipping.writeback.approve` 的人员不得豁免 MFA。
- SSO 只有在已验证的 `amr/acr` 明确证明完成 MFA 时才可替代 ERP 二次验证。
- 恢复码一次性使用、只保存哈希、下载后不再显示；管理员不能查看用户恢复码原文。

### 1.3 登录流程

1. `POST /api/v1/auth/login` 接收登录标识和密码，不接收角色、店铺或权限。
2. 失败响应统一使用 `invalid_credentials`，不得暴露账号是否存在、锁定或未邀请。
3. 密码通过后进入 `mfa_pending`，该状态不能访问任何业务接口。
4. `POST /api/v1/auth/mfa/verify` 通过后，服务端废止登录前临时状态，创建新的正式会话并旋转所有凭证。
5. 登录成功响应只返回安全用户摘要；权限和店铺来自服务端的 `/auth/session`。
6. 登录、失败、MFA 失败和成功均写无密码、无 Token、无完整 IP 的安全审计事件。

防暴力规则：

- 同时按账号哈希和来源网络做速率限制。
- 5 次连续失败后逐步延迟，10 次/15 分钟后临时阻断 15 分钟。
- 不因单一来源 IP 的攻击永久锁死账号；永久 `locked` 只能由管理员或风险策略明确设置。
- 成功登录后清除短期失败计数，但保留安全审计。

### 1.4 会话时限

固定时限：

| 类型 | 时限 | 规则 |
| --- | --- | --- |
| MFA 待验证会话 | 5 分钟 | 不可续期，只可访问 MFA 与取消登录接口 |
| 空闲时限 | 30 分钟 | 有效的人工业务请求可延长；轮询、健康检查和静态资源不延长 |
| 绝对时限 | 12 小时 | 从登录完成计算，任何活动都不能延长 |
| 敏感操作新鲜认证 | 15 分钟 | 导出客户信息、平台回填、权限修改、凭证修改前要求最近完成密码/SSO+MFA |
| CSRF Token | 跟随当前会话 | 登录、权限升级、重新认证和会话旋转时同步更换 |

V1 不提供“长期记住我”。浏览器关闭不必立即撤销服务端会话，但 Cookie 使用 Session Cookie；服务端仍以空闲/绝对时限为准。

同一用户最多保留 3 个有效生产会话。第 4 次登录成功时撤销最早会话，并在账号安全页显示设备摘要和最近活动时间。

### 1.5 退出

- `POST /api/v1/auth/logout` 撤销当前服务端会话、清除 Cookie，并使当前 CSRF Token 和所有未使用审批挑战失效。
- “退出所有设备”撤销该用户全部会话和审批挑战，并递增用户 `session_version`。
- 退出接口必须幂等；已过期会话再次退出仍清理 Cookie。
- 仅删除浏览器 Cookie不算退出，服务端会话必须标记 `revoked_at`。
- 退出后浏览器返回上一页时，受保护页面不得从缓存显示 PII；相关响应使用 `Cache-Control: no-store`。

### 1.6 自动和强制失效

以下事件必须立即使相关会话失效：

- 用户变为 `inactive` 或 `locked`。
- 密码重置、MFA 重置、认证提供方变更。
- 管理员执行“撤销全部会话”。
- 检测到会话泄露或异常登录。
- 用户的全局 `session_version` 变化。

以下事件必须立即使旧授权失效，但可保留登录状态并要求重新加载权限：

- 店铺成员关系撤销或变为 inactive。
- 角色变化、角色停用、权限增加或删除。
- 店铺被停用。

实现方式：用户和授权关系维护单调递增的 `authz_version`。会话记录保存签发时版本；每个敏感请求必须比较当前版本。普通读取可缓存授权最多 60 秒，但必须以版本为缓存键；写操作、PII 查看/导出和平台回填不得使用超过当前请求的旧授权缓存。

## 2. 用户、店铺和权限确认

### 2.1 服务端身份解析

统一依赖 `require_session()` 必须完成：

1. 从 Cookie 读取不透明会话值。
2. 对值做 SHA-256/HMAC 哈希后查询会话表；数据库不得保存原始凭证。
3. 检查撤销、空闲、绝对到期、环境、用户状态和 `session_version`。
4. 加载当前用户 ID、认证级别、MFA 时间和 `authz_version`。
5. 更新 `last_seen_at`，但对高频请求做节流，避免每次轮询写数据库。

业务代码只能使用依赖返回的 `AuthenticatedPrincipal`。禁止从请求体、查询参数或自定义用户头重新构造身份。

### 2.2 店铺范围

- 可访问店铺来自有效的 `erp_store_memberships`。
- 每个成员关系必须同时满足用户 active、成员 active、角色 active、店铺 active。
- 普通运营只能访问明确分配的店铺。
- Owner 的全店范围必须是服务端系统角色能力，不能由 `store_ids=all` 请求参数触发。
- 顶部店铺切换只改变界面上下文，不授予权限。

涉及资源 ID 的接口必须先从数据库加载资源，再使用资源真实的 `store_id` 授权。例如发货回填根据 `batch_id` 加载批次店铺，不能相信请求体传入的店铺。

批量请求中所有对象必须属于同一已授权店铺；混入一个跨店对象时整批阻断，禁止悄悄忽略。

### 2.3 权限计算

最终权限等于：

```text
有效会话
∩ active 用户
∩ active 店铺成员关系
∩ active 角色
∩ active 权限
∩ 当前资源店铺
∩ 操作需要的认证级别
```

前端可调用 `GET /api/v1/auth/session` 获取：

- `user_id` 的安全公开标识、显示名。
- 当前会话到期时间和 MFA 新鲜度。
- 已分配店铺安全摘要。
- 每个店铺的权限键，用于隐藏无权按钮。

该响应只用于界面呈现。后端每个接口仍必须独立校验，不能因为前端已隐藏按钮而省略授权。

### 2.4 错误合同

| HTTP | 业务码 | 场景 |
| --- | --- | --- |
| 401 | `session_required` | 无 Cookie 或无有效会话 |
| 401 | `session_expired` | 空闲或绝对过期 |
| 401 | `session_revoked` | 会话已撤销或版本失效 |
| 401 | `reauthentication_required` | 敏感操作认证超过 15 分钟 |
| 403 | `mfa_required` | 尚未达到生产认证级别 |
| 403 | `store_scope_forbidden` | 资源店铺不在用户范围 |
| 403 | `permission_forbidden` | 当前店铺缺少权限 |
| 403 | `csrf_validation_failed` | 写请求 CSRF/Origin 验证失败 |
| 409 | `resource_version_changed` | 审批后业务对象已变化 |

错误响应不得返回会话值、Cookie、密码、MFA Secret、内部权限查询语句或客户隐私。

## 3. 浏览器安全登录方式

### 3.1 Cookie 固定合同

生产 Cookie：

```text
名称: __Host-erp_session
Secure: true
HttpOnly: true
SameSite: Lax
Path: /
Domain: 不设置
Max-Age: 不设置（Session Cookie）
```

Cookie 值至少 256 bit 随机熵，只包含随机不透明值，不包含用户 ID、角色、店铺、权限或可解码 JWT。Cookie 每次完成登录、重新认证和权限提升后旋转；旧值立即失效。

浏览器 JavaScript 不得读取会话凭证，不得把身份凭证写入 `localStorage`、`sessionStorage`、IndexedDB、URL、Redux 持久化或前端日志。

### 3.2 CSRF

所有会改变状态的 `POST/PUT/PATCH/DELETE` 必须同时满足：

1. 有效会话 Cookie。
2. `Origin` 属于精确生产允许列表；缺失 Origin 的浏览器写请求默认拒绝。
3. `X-CSRF-Token` 与当前会话绑定的同步 Token 匹配。
4. 请求 `Content-Type` 属于端点明确允许类型。

CSRF Token 由 `/auth/session` 返回，前端只保存在内存；刷新页面后重新读取。它不是身份凭证，仍不得出现在 URL 或日志。登录端点使用登录 CSRF/Origin 校验和 SameSite Cookie，避免登录 CSRF。

GET/HEAD 必须保持只读，禁止通过 GET 触发同步、导出、下载计数、回填或退出。

### 3.3 网络和浏览器响应头

- 生产只允许 HTTPS；启用 HSTS。
- CORS 仅允许明确的 ERP 前端 Origin，`allow_credentials=true`，禁止 `*`。
- 设置 CSP，至少限制 `default-src 'self'`、禁止不受控脚本来源和内联脚本。
- 设置 `frame-ancestors 'none'` 或等价 `X-Frame-Options: DENY`。
- 设置 `X-Content-Type-Options: nosniff`、严格 Referrer Policy。
- 登录、会话、订单 PII、发货和权限响应使用 `Cache-Control: no-store, private`。
- 文件下载使用安全文件名、`Content-Disposition: attachment` 和 `nosniff`。

## 4. 防止修改和回填请求伪造

### 4.1 统一写操作门禁

每个修改接口必须按顺序执行：

1. 验证生产会话。
2. 验证 CSRF 和 Origin。
3. 从数据库加载目标资源。
4. 用资源真实店铺检查成员关系和权限。
5. 检查用户/MFA 新鲜度。
6. 检查资源版本、业务状态和幂等键。
7. 对敏感操作验证服务端审批挑战。
8. 执行操作并写无敏感数据审计。

任一步失败都不得产生业务写入。权限检查不能依赖前端是否展示按钮，也不能依赖请求中的 `role`、`store_id`、`manual_approval=true` 或 `final_confirmation=true`。

### 4.2 敏感操作审批挑战

客户信息导出、Naver 发货回填、凭证修改、权限修改等操作使用两段式流程：

1. 预检接口根据当前服务端状态生成确认摘要。
2. 用户确认后，服务端签发一次性 `approval_challenge`。
3. 执行接口验证挑战后重新检查权限和资源状态。

挑战必须绑定：

```text
session_id_hash
+ user_id
+ action_scope
+ store_id
+ resource_id
+ resource_version
+ candidate_hash
+ expires_at
+ used_at
```

固定规则：

- 有效期最长 10 分钟。
- 只能使用一次。
- 绑定当前会话，不允许同一用户的另一个浏览器会话使用。
- 候选订单、物流单号或批次版本变化后立即失效。
- 登出、强制撤销、权限变化或重新认证后旧挑战全部失效。
- `candidate_hash` 在执行时必须由服务端重新计算并比较，不能只保存不验证。

前端确认复选框只是用户意图输入，不是授权凭证。执行权限来自会话，操作范围来自挑战和数据库。

### 4.3 重放、并发和幂等

- 平台写入每个订单使用稳定幂等键：`platform + store_id + product_order_id + action + payload_hash`。
- 执行时使用行锁/乐观版本防止两个运营同时回填。
- 已成功项不得因整批重试再次发送；只重试明确失败且重新预检的项。
- 审批挑战使用和业务提交应尽可能在同一事务中标记，避免并发双用。
- 真实平台调用前后都记录请求关联 ID，但不记录凭证、完整请求体或客户 PII。

### 4.4 审计

认证与敏感操作审计允许保存：用户内部 ID/哈希、会话 ID 哈希、店铺、动作、资源哈希、数量、结果、错误码、时间、设备摘要和关联 ID。

禁止保存：密码、MFA Secret/验证码、会话 Cookie、CSRF Token、approval challenge 原文、Authorization、完整 IP、浏览器完整指纹、客户姓名/电话/地址、平台原始响应。

## 5. 开发测试身份与生产身份隔离

### 5.1 环境固定

进程启动时只允许一个不可动态切换的环境：`development`、`test` 或 `production`。环境由部署配置决定，不能由请求头、URL 参数、Cookie 或页面设置改变。

生产启动必须检查并拒绝以下配置：

- `ALLOW_DEV_AUTH=true` 或任何 mock/test 身份开关。
- 开发默认会话密钥、测试用户密钥或空密钥。
- 非 HTTPS Cookie、缺少 `Secure`/`HttpOnly`、Cookie 使用非 `__Host-` 名称。
- CORS 通配来源或 localhost 来源。
- 数据库 URL 指向测试文件、SQLite 临时库或开发数据库标记。
- 开启自动创建测试用户、自动登录或跳过 MFA。
- 注册 `/__dev__/*`、`/mock-auth/*` 等开发身份路由。
- 接受 `X-ERP-User-Key`、`X-Debug-Role`、`actor_context.role` 等身份替代方式。

### 5.2 开发身份

开发身份只能在全部条件满足时启用：

1. `APP_ENV=development`。
2. `ALLOW_DEV_AUTH=true`。
3. 监听 loopback 或受控本机开发网络。
4. 使用独立开发数据库，数据库包含 `environment=development` 标识。
5. 使用不同 Cookie 名 `erp_dev_session`、不同签名/哈希密钥和不同 Origin。

开发登录必须通过显式 `/__dev__/session` 路由创建短期开发会话；不能把任意用户头直接当身份。开发页面必须持续显示“开发身份”，审计标记 `environment=development`。

生产构建最好不注册开发路由；若因代码共享存在路由定义，生产必须返回 404，不能只返回 403 暴露能力。

### 5.3 测试身份

- 自动化测试只使用临时数据库、固定虚构用户和虚构客户数据。
- `APP_ENV=test` 时真实平台读写、生产 Cookie 域名和生产密钥必须不可用。
- 测试不得读取生产 `.env`、生产数据库备份或浏览器生产 Cookie。
- 测试会话密钥每次测试运行生成，测试结束销毁。
- 集成测试必须证明开发/测试会话不能在生产配置中解析。

## 6. Terra 实现标准

### 6.1 数据模型

至少新增或完善：

#### `erp_user_security`

- `user_id`
- `password_hash`（Argon2id，仅本地密码用户）
- `mfa_type`
- `mfa_secret_encrypted` 或 WebAuthn 凭证关联
- `mfa_enabled_at`
- `session_version`
- `authz_version`
- `failed_login_count`
- `blocked_until`
- `password_changed_at`

#### `erp_sessions`

- `id`
- `session_token_hash`（唯一，禁止原文）
- `user_id`
- `environment`
- `authn_level`（`mfa_pending` / `mfa_verified`）
- `session_version`
- `authz_version_at_issue`
- `csrf_token_hash`
- `created_at`
- `last_seen_at`
- `idle_expires_at`
- `absolute_expires_at`
- `last_reauthenticated_at`
- `revoked_at`
- `revoke_reason`
- `device_label`、截断/哈希网络摘要（不得保存完整指纹）

#### `erp_approval_challenges`

- 本文 4.2 的全部绑定字段。
- Token 只保存哈希。
- 对未使用且未过期挑战建立查询索引。

会话、CSRF 和审批 Token 均使用密码学安全随机数生成器，不得使用自增 ID、时间戳、UUIDv1 或可预测哈希作为凭证。

### 6.2 API

必须提供：

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/mfa/verify`
- `GET /api/v1/auth/session`
- `POST /api/v1/auth/logout`
- `POST /api/v1/auth/logout-all`
- `POST /api/v1/auth/reauthenticate`
- `GET /api/v1/auth/sessions`（安全设备摘要）
- `DELETE /api/v1/auth/sessions/{session_id}`（撤销指定会话）

管理员强制撤销用户会话必须使用独立管理权限、MFA 新鲜认证和审计。

### 6.3 统一中间件/依赖

Terra 必须提供并强制业务路由使用：

- `require_session`
- `require_mfa`
- `require_recent_auth`
- `require_store_permission`
- `require_csrf_for_write`
- `issue_approval_challenge`
- `consume_approval_challenge`

订单、仓库发货、客服、PII、平台回填、凭证、权限和系统设置接口不得各写一套身份解析。旧 `X-ERP-User-Key` 入口必须从生产路由删除，不得保留为 fallback。

### 6.4 密钥与日志

- 会话哈希 Pepper、CSRF 密钥、MFA 加密密钥分开管理并来自生产 Secret Manager/部署密钥。
- 支持密钥轮换；轮换时可有短暂双密钥验证窗口，但新会话只用新密钥。
- 请求日志在进入应用日志前删除 Cookie、Set-Cookie、Authorization、CSRF 和审批头。
- 登录请求体、MFA 请求体、会话响应不得被 APM/代理记录。

## 7. 必须通过的测试

### 7.1 身份与会话

1. 未登录访问受保护接口返回 401。
2. 页面提交 `user_id`、角色、店铺、`X-ERP-User-Key` 均不能建立生产身份。
3. 登录成功后数据库只有会话哈希，没有 Cookie 原文。
4. 登录前会话在登录后旋转，旧值不可用，防止会话固定。
5. `mfa_pending` 不能访问任何订单、发货、客服和管理接口。
6. 30 分钟空闲和 12 小时绝对时限分别生效；轮询不延长空闲时间。
7. 退出后服务端会话、CSRF 和审批挑战全部失效。
8. “退出所有设备”使该用户所有现有会话失效。
9. 用户锁定、密码重置、MFA 重置立即使旧会话失效。
10. 第 4 个有效会话登录后，最早会话被撤销。

### 7.2 店铺与权限

11. 用户只能访问 active 成员关系对应的店铺。
12. 修改请求中的 `store_id` 不能绕过资源真实店铺校验。
13. 撤销成员关系或权限后，旧页面仍开着也无法继续读取 PII或写入。
14. 无 `recipient_pii.view` 不能访问完整收件接口。
15. `recipient_pii.view` 不自动获得 `recipient_pii.export`。
16. `shipping.batch.manage` 不自动获得 `shipping.writeback.approve`。
17. 停用角色、权限或店铺立即阻断对应请求。

### 7.3 浏览器和伪造防护

18. 生产 Cookie 精确符合 `__Host-`、Secure、HttpOnly、SameSite、Path 和无 Domain 合同。
19. localStorage、sessionStorage、URL 和前端日志中扫描不到会话、CSRF 和审批凭证。
20. 无 CSRF、错误 CSRF、错误 Origin、跨站表单和跨站 fetch 的写请求全部失败。
21. CORS 不接受通配来源、localhost 和未配置 Origin。
22. GET 请求不能触发任何业务写入。
23. PII 和认证响应包含 `Cache-Control: no-store`，退出后浏览器后退不能读取缓存内容。
24. 会话 Cookie、密码、MFA、CSRF、审批 Token 不出现在应用日志、代理日志和审计日志。

### 7.4 敏感操作

25. 导出和回填使用不同权限与不同 action scope 的审批挑战，不能互换。
26. 审批挑战不能跨用户、跨会话、跨店铺、跨批次使用。
27. 执行时重新计算 `candidate_hash`；候选行、物流单号或版本变化后挑战失败。
28. 审批挑战只能使用一次，并发提交最多一个成功。
29. 最近认证超过 15 分钟时，PII 导出和平台回填要求重新认证。
30. 批量回填部分成功后，重试只发送失败项且使用新挑战和新幂等键校验。

### 7.5 环境隔离

31. 生产配置启用 `ALLOW_DEV_AUTH` 时应用拒绝启动。
32. 生产配置存在开发路由、不安全 Cookie、通配 CORS、测试密钥或测试数据库时拒绝启动。
33. 开发/测试 Cookie 和 Token 在生产密钥、生产 Cookie 名和生产数据库中全部无效。
34. 测试启动无法连接生产数据库或读取生产凭证。
35. 所有认证和授权测试使用临时数据库、虚构人员与禁用真实平台写入的环境。

## 8. 上线门禁

T03.6 只有在以下条件全部满足后才可通过生产验收：

1. 35 项测试全部通过。
2. 所有受保护业务接口完成统一会话依赖清单审计。
3. 生产 OpenAPI 中不存在开发身份路由和 `X-ERP-User-Key` 身份合同。
4. 前端代码扫描不到生产身份头、localStorage Token 和客户端角色授权逻辑。
5. 生产配置启动失败测试通过。
6. 密钥轮换、账号锁定、权限撤销和会话强制退出演练通过。
7. 订单 PII 导出与 Naver 回填分别完成一次不调用真实平台的端到端安全演练。

在此之前，即使仓库发货业务代码和页面都已完成，也只能视为本地/测试可用，不能开放生产账号登录或真实平台写入。
