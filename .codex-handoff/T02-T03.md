## 4. 现有危险问题

### P0：跨店回填范围混淆

`ShippingAssistant` 可按页面店铺筛选展示订单，但回填使用 `selectedStoreId || query.storeId`。当顶部当前店铺和页面筛选店铺不同，显示订单的范围可能与写入店铺不同。

### P1：前端声明式确认不应等同授权

前端对回填请求直接传入所有确认标志 `true`。服务端应绑定登录角色、批次版本、当前订单状态和二次确认，而不是信任客户端布尔值。

### P1：订单匹配合同不一致

本地状态匹配仅使用 `external_order_id` 或本地 ID，没有使用 `product_order_reference`；Naver 回填候选又支持商品订单号。

### P1：重复与取消保护不足

- 重复检查只覆盖当前上传，未检查历史导入、未完成批次或重复回填。
- 本地终态订单会被阻断；但平台写入前没有刷新并重验平台实时状态，取消可能发生在 dry-run 与写入之间。

### P0：隐私边界回归

全量后端验证失败表明 Naver 订单预览暴露收件人姓名、电话、地址和邮编；测试预期 `address_saved=False`。同时，导出服务当前会拒绝收件隐私字段，无法生成真实仓库表。

### P1：文件安全性

导出文件写入服务端文件系统并返回路径；需要受控下载令牌、权限检查、访问审计、到期删除和文件内容加密策略。

## 5. 建议数据库与 API 合同

新增或明确以下实体：

- `shipping_batches`：`batch_no`、`store_id`、`platform`、状态、创建/发仓/回传/确认时间和操作者。
- `shipping_batch_orders`：批次订单快照、内部 SKU、数量、行状态；对未完成批次内的同一订单设置唯一约束。
- `tracking_imports` / `tracking_import_rows`：必须关联 `shipping_batch_id`，保存解析、匹配、阻断/确认状态。
- `shipment_writeback_attempts`：每订单/商品订单号的幂等键、请求时间、结果、HTTP 状态、错误码、审计关联。

建议接口：

- `POST /shipping/batches`：提交订单 ID，服务端验证同店铺/平台/状态并创建批次。
- `GET /shipping/batches`、`GET /shipping/batches/{id}`：运营队列与批次详情。
- `POST /shipping/batches/{id}/export`：仅在 PII 权限、审计和确认通过后生成受控下载令牌。
- `POST /shipping/batches/{id}/tracking-imports`：上传并返回只读预览。
- `POST /shipping/batches/{id}/validate`：输出正常、待确认、阻断三组。
- `POST /shipping/batches/{id}/local-dispatch`：人工确认后写本地状态。
- `POST /shipping/batches/{id}/writeback`：服务端重新检查当前订单状态、权限和批次版本后逐行写平台。

PII 仅放入加密、短期、受权限与审计控制的仓库文件；普通 API、审计表、日志和历史列表只保留脱敏值或哈希。
